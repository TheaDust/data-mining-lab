## 条件与建议的定义

条件是对建议适用范围的限制，例如天气、游客类型、体力、可用时间、路线调度。建议是满足该条件时可选、推荐或应避免的行为，也可以是适合该条件的原文方案名称。

“建议坐船”本身没有条件，“可以看到小鱼”是可见性描述，“因为阴雨天舍弃原始森林”是经历叙述，均不直接生成条件建议对。程序没有把未出现的“带老人”“下雨”等条件补进原文。

规则按以下方式配对：

1. **显式条件。** 识别“如果/假如/若/倘若/要是”，以逗号、则/那么/就或建议触发词区分两部分。同一句的多组条件分别处理。条件独占一行时，可关联紧邻下一单元；空行、新标题或编号段落会阻断关联。
2. **隐式限定。** 使用固定领域短语匹配“体力一般建议……”“时间充裕可……”“带老人小孩慎选”“晴天带伞”等。条件必须紧邻建议表达，或只隔“出门前”这类限定。普通“可以”不独立创建条件。
3. **适用人群。** 对“路线/景点适合 X”提取 X 为条件、原文路线或景点标题为推荐对象，关系标为 `suitable_option`。不自动改写成原文没有的祈使句。标题被新章节清除，避免将故宫温馨提示错误绑定到雁翅楼。
4. **路线段限制。** 对“天鹅海→箭竹海不建议徒步”等提取路线段与推荐/禁止行为。否定和协调建议保留，例如“千万别硬走，乖乖坐车”“建议坐观光车，或者分成2天慢慢玩”。

匹配采用有限的局部规则，不是开放域语义解析。句段分隔包括换行、句末标点及非数字间的波浪号；数值范围中的波浪号保留。条件和建议分别定位，输出证据窗口扩到完整原文行，避免“！”前的景点名或票务对象丢失；跨行或标题型关系可能包含多行。

## 分类口径

仅根据条件文本分类，建议里的关键词不反向污染条件类型。一个条件可以有多个类型；`condition_type` 是统计使用的主类别，`condition_types` 保留其他适用类别。

| 类型 | 含义 | 本批样例 |
|---|---|---|
| `weather` | 天气与光线 | 晴天、光线偏暗 |
| `visitor_type` | 游客类型与偏好 | 带娃、老人小孩、初次来、对历史感兴趣 |
| `physical_condition` | 体力与步行偏好 | 体力一般、不想走路、长距离 |
| `time` | 时间安排 | 时间充裕、赶时间、不赶时间 |
| `transport` | 交通与预约 | 打算坐船、没约上 |
| `crowd` | 人流条件 | 旺季参观、怕人多想清净 |
| `season` | 季节性条件 | 每年3–4月郁金香展 |
| `budget` | 预算约束 | 想省钱不花额外门票 |
| `route` | 路线、调度与地形 | 分配到右线、指定路线段、漫步群山 |

分类规则在 `TYPE_PATTERNS` 中，主类别顺序为天气、游客、体力、时间、交通、人流、季节、预算、路线；明确路线条件优先。无法归入上述类别的明确条件使用 `other`，当前没有该类结果，不绘制空类别。

类别是本批实验的操作性定义。例如“赶时间想省腿”同时涉及体力和时间，统计主类为体力。跨景区比较只表示当前样本数量，不是不同景区真实需求比例。

## 输出与来源

核心字段沿用根目录 `SCHEMA.md`：`advice_id`、`doc_id`、`scenic_spot`、`condition_type`、`condition`、`advice`、`source_sentence`、`start/end`。

- `start/end` 对应 `source_sentence` 的证据窗口，不是仅对应条件或建议。
- `condition_span`、`advice_span` 各保存独立的 `text/start/end`，可以分别恢复两部分。位置基于原样 `clean_text` 的 Python Unicode 码点，从 0 开始，左闭右开。
- `source_sentence` 是连续原文窗口，可能含多句或多行。它保留对象和篇章边界，不表示一定是语法意义上的一个句子。
- `context` 是可用的路线/景点标题及位置。它可能位于证据窗口之前；`usable` 表示是否可作为绑定目标。
- `relation=recommendation` 为行为建议；`suitable_option` 为条件对应的原文适用方案。
- `requires_context=true` 表示建议仍依赖更大范围指代，例如“新手可以直接抄”。它没有被视为已完成共指消解。
- `review_status=automatic` 是规则结果，`reviewed` 表示本轮应用了 `reviews.json` 的确认或新增/替换决定。程序不会默认把任何结果标为人工确认。
- `mapping_id` 按条件、建议、语境等内容生成，`occurrences` 引用逐位置记录。下游应通过提及 ID 读取来源 URL 和原文锚点。

## 去重边界

先按规则优先级处理同位置的重复候选：显式条件优先，适用人群/路线段次之，隐式规则最后。同一条件的重叠匹配、相同或包含的建议只保留一个提及。

再对跨位置结果建立映射组。前提是同景区、同主类别、同规范化条件、同标题语境及同关系。规范化统一全半角、空白、部分标点及开头的“建议/可以”等表达，保留否定和路线符号。建议规范化后完全一致时合并；前后缀近重复只在一方是另一方前缀、长度比至少 0.85，且数字和否定信号一致时合并。所有原始提及仍保留。

当前九寨沟重复的“天鹅海→箭竹海不建议徒步”由两个位置合并为一条映射。不同路线的“慎选”、相反建议、不同数字约束不会因此混成一条。语义近义但字面差异较大的表达仍分开，例如“坐观光车”和“坐西湖环湖观光小车”。

## 人工复核与补充

初始 `reviews.json` 为 `[]`，不宣称人工复核已完成。先参考 `results/human_review.md`，结合 JSON 的 ID、原文与位置核对。该清单是定向样例，不是独立 gold。

确认或剔除已有提及：

```json
[
  {"action": "confirm", "advice_id": "从输出复制实际 ID", "note": "核对条件、建议与来源"},
  {"action": "reject", "advice_id": "另一条实际 ID", "note": "说明误抽原因"}
]
```

新增漏项需要 `action=add`、`doc_id`、`condition_start/end`、`advice_start/end`；可选 `condition_type`、`relation`、`note`。位置均为全文索引，可由 `clean_text.index(原文短语)` 辅助查找，并检查同形短语是否多次出现。`replace` 使用相同字段，并增加被替换的 `advice_id`。保存后重跑会验证位置和引用，应用结果记录在 `review_log.json`。

替换同一文档、同一条件位置的记录时，保留原有标题语境；条件位置移动或新增记录时，按当前位置重新解析标题。`replace` 默认保留原记录的 `relation`，需要修改时可显式填写。新增和替换均可用 `context_start`、`context_end` 指定当前文档中的语境跨度，覆盖自动绑定；程序会检查该原文切片。未绑定具体对象的“慎选”会标记为 `requires_context=true`。

不要直接修改派生 JSON 充当复核记录，因为下一次运行会重建。`human_review.md` 的手写文字会保留，但决定是否生效以 `reviews.json` 为准。

## 验证与限制

31 项相关测试覆盖多建议与否定、若/假如、同句多条件、跨行及新标题、普通建议排除、实际叙述排除、适用人群、标题作用域、季节与交通、近重复分组、来源和人工复核决定，包括替换保留语境、跨路线重新绑定、手工指定标题和缺失对象标记。每次运行还检查逐位置记录的字段与原文锚点。

当前结果有 43 处提及、42 条映射，全部 140 个原文锚点匹配。没有完整人工标注集，因此没有 Precision/Recall/F1。已知漏项包括“哪天晴天选哪天”的关联表达、“有特展时超值得去”的隐式推荐，以及需要跨更远段落理解的条件。短语边界、建议对象和分类仍需人工确认。

来源内容是实验归档文本，其中票务、价格、开放和健康相关表达只作为抽取对象，不是经实时核实的出行指导。
