# 第6章 多源程序性知识的融合与图谱可视化

## 6.1 任务目标与输入数据

本章把前五个实验的输出整合成一张可查询、可追溯的景区游览知识图谱。与只做“关系抽取”不同，图谱需要同时回答三类问题：

1. **景区里有什么**：POI 及其别名、被多少文档和路线提及；
2. **怎么走**：官方路线与游客路线中 POI 的先后顺序、活动、时段；
3. **什么条件下怎么选**：task5 抽取的条件性建议，以及建议涉及的 POI。

输入数据如表 6-1 所示。task5 在任务书中是“必要时融合”的可选输入；本次 task5 已由组内同学交付 41 条条件关系，因此一并入图。

## 6.2 多源融合策略

### 6.2.1 以偏移量做 task2–task3 精确对齐

task3 在抽取路线步骤时，为每个 POI 保留了 `entity_ref = {start, end, type}`，指向 task2 实体在原文中的字符区间。本章直接用 `(doc_id, start, end, type)` 四元组做精确连接，而不是按名称模糊匹配。

- 路线步骤共 298 个 POI 提及；
- 其中 291 个带 `entity_ref`，**291 个全部命中 task2**，命中率 100%；
- 3 个提及没有 `entity_ref`（2 个是别名归一后的天鹅海、1 个是五花海），按名称归并到同一 POI 节点；
- 4 个提及是边界动作（出沟 3 次、进景区 1 次），不建 POI 节点。

这条对齐链路把 task2 的“实体层”和 task3 的“程序层”真正接在一起：每个 `Step` 都能回指文档中的字符区间，而不是只共享一个 `doc_id`。

### 6.2.2 POI 规范化、去重与跨来源合并

task2 的 1,112 个 POI 提及按 `(景区, 规范化名称)` 聚合后得到 342 个候选。规范化只做两类保守处理：

- 去掉名称中的空白字符；
- 使用 task3 已记录的别名：九寨沟“天鹅湖 → 天鹅海”“诺日朗中心 → 诺日朗中心站”。

没有做“去掉行政前缀”“合并父子景点”等激进归一，避免把“故宫”和“北京故宫”、“西湖”和“西湖十景”错误合并。

聚合后每个 POI 节点保留：

- `mention_count`：task2 中的提及次数；
- `document_count`、`doc_ids`：出现在哪些文档；
- `source_types`：official / user_generated；
- `aliases`：同一节点的其他写法；
- `in_route`、`route_count`、`step_count`：被 task3 路线引用的情况。

结果是 **215 个 POI 节点**，其中 148 个被至少一条路线引用，67 个只来自 task2 提及；**70 个 POI 同时被官方文档和游客文档提及**，说明跨来源合并确实把两边说的是同一个景点识别了出来。例如“太和殿”有 12 次提及、出现在 2 条路线中，来源同时包含 official 与 user_generated；“原始森林”在九寨沟的 5 条路线中全部出现，提及 22 次。

文档到 POI 的 `MENTIONS` 边按“文档—POI”聚合，共 436 条，边上保留 `count` 与 `source_type`，因此既能做来源追溯，也不会让同一文档的重复提及把图撑大。

### 6.2.3 噪声、低频候选与异常过滤

融合过程做了三项显式过滤，并全部写入质量报告：

1. **低频 POI**：只出现 1 次、且没有被任何路线引用的 POI 候选（125 个）不进入主图，写入 `results/excluded_pois.csv`。保留规则是“路线引用优先，其次提及 ≥2 次”，避免把游记里偶然提到的餐馆、酒店、地铁站都当成景点。
2. **边界动作**：task3 把“出沟”“进景区”放在 `pois` 字段里，但它们是动作而非景点。本章过滤 4 个此类提及，对应步骤仍保留在路线序列中，只是没有 `VISITS` 边。
3. **无 POI 步骤**：task3 本身有 3 个步骤的 `pois` 为空（到达景区、出景区、摆渡车）。加上前面的边界步骤，共 7 个步骤没有 `VISITS` 边；它们仍通过 `HAS_STEP`、`NEXT` 和 `HAS_ACTIVITY` 保留在路线中，不用虚构 POI 补齐。

此外，2 条九寨沟路线的首/尾步骤是“进景区/出沟”，本章不给它们强行生成 `STARTS_AT`/`ENDS_AT`，因此 23 条路线中只有 21 条有起终点边。这是有意保留的数据缺口，而不是构图遗漏。

### 6.2.4 task5 条件建议的融合

41 条条件建议全部建成 `Condition` 节点，属性保留 `condition`、`recommendation`、`condition_type`、`source_text`、`review_status`、`audit_candidate` 等字段。条件通过三类边接入图谱：

- `HAS_CONDITION`：景区 → 条件；
- `HAS_TYPE`：条件 → 条件类型（7 类：时间约束 13、游客类型 7、体力与健康 6、交通条件 5、游览偏好 4、天气环境 3、其他条件 3）；
- `FROM_DOC`：条件 → 原文档，保留来源。

条件与具体 POI 的连接采用保守的最长字符串匹配：只在 `recommendation` 和 `condition` 文本中找 POI 名称，去掉“故宫/九寨沟/西湖/景区/左线/右线”等泛称，最长匹配优先、不重叠、每条条件最多 3 个 POI。结果 **20 条条件链接到具体 POI，共 30 条 `RELATES_TO` 边**；其余 21 条只保留景区和文档级归属。每条边都记录 `matched_text` 与 `match_field`，便于人工复核。

例如：

- R00008“时间有限 → 选珍宝馆”链接到“珍宝馆”；
- R00017“带小朋友 → 去花港观鱼喂锦鲤”链接到“花港观鱼”；
- F00010“吃饭 → 选择冰窖餐厅”链接到“冰窖餐厅”。

task5 的 `review_status` 仍是“独立 LLM 辅助审核及证据复核；待真实人工确认”。本章原样保留该状态，不把条件关系当作人工金标准，也不在质量检查中宣称条件准确率。

## 6.3 图谱 Schema

图谱采用带属性的有向多重图（NetworkX `MultiDiGraph`），节点和边都带 `scenic_spot`，保证三个景区可以独立取子图。

### 6.3.1 节点类型

**表 6-2 节点类型（583 个）**

| 节点类型 | 数量 | 说明 | 主要属性 |
|---|---:|---|---|
| `ScenicSpot` | 3 | 景区根节点 | `route_count`、`document_count`、`condition_count` |
| `POI` | 215 | 规范化景点 | `mention_count`、`route_count`、`aliases`、`source_types` |
| `Route` | 23 | 官方/游客路线 | `route_id`、`route_kind`、`source_type`、`step_count` |
| `Step` | 250 | 路线中的一步 | `order`、`day`、`time_period`、`activity_raw`、`pois` |
| `Activity` | 12 | 归一化活动 | `category` |
| `TimePeriod` | 3 | 时段 | `period`（上午/中午/下午） |
| `Condition` | 41 | 条件性建议 | `pair_id`、`condition`、`recommendation`、`review_status` |
| `ConditionType` | 18 | 条件类型（按景区实例化） | `label` |
| `Document` | 18 | 原文档 | `title`、`source_type`、`text_type`、`url` |

`Activity` 和 `ConditionType` 按景区实例化（例如“北京故宫/游览参观”与“九寨沟/游览参观”是两个节点），这样每个景区子图都是自包含的；代价是同类节点会有重复，但换来了清晰的连通分量和更简单的查询。

### 6.3.2 边类型

**表 6-3 边类型（1,751 条）**

| 边类型 | 数量 | 方向 | 说明 |
|---|---:|---|---|
| `HAS_ROUTE` | 23 | 景区 → 路线 | 路线归属 |
| `HAS_STEP` | 250 | 路线 → 步骤 | 属性 `order` |
| `NEXT` | 227 | 步骤 → 下一步 | 路线内顺序链 |
| `VISITS` | 294 | 步骤 → POI | 属性 `order_in_step`、`aligned_to_task2` |
| `STARTS_AT` | 21 | 路线 → POI | 首步 POI |
| `ENDS_AT` | 21 | 路线 → POI | 末步 POI |
| `HAS_ACTIVITY` | 272 | 步骤 → 活动 | 一个步骤可多标签 |
| `AT_TIME` | 31 | 步骤 → 时段 | 仅显式时段 |
| `HAS_CONDITION` | 41 | 景区 → 条件 | 条件归属 |
| `HAS_TYPE` | 41 | 条件 → 条件类型 | 条件分类 |
| `RELATES_TO` | 30 | 条件 → POI | 条件建议涉及的 POI |

| `FROM_DOC` | 41 | 条件 → 文档 | 条件来源 |

节点 ID 采用可读前缀：`spot:北京故宫`、`poi:北京故宫:午门`、`route:<route_id>`、`step:<route_id>:<step_id>`、`condition:R00008`、`doc:<doc_id>`。边 ID 按构图顺序生成（`e000001` 起），节点和边输出前按 ID 排序，保证同一输入得到同一份 CSV/JSON。

一条典型路径在图中表示为：

```text
(spot:北京故宫)
  -[HAS_ROUTE]-> (route:gugong_official_..._route_01)
  -[HAS_STEP {order:1}]-> (step:...:1)
  -[VISITS]-> (poi:北京故宫:午门)
  -[HAS_ACTIVITY]-> (activity:北京故宫:游览参观)
```

## 6.4 构图实现与可复现性

构图代码在 `task6/build.py`，查询接口在 `task6/graph.py`，一键流水线在 `task6/run.py`：

```bash
python -m task6.run              # 构图 + 18 项检查 + 可视化
python -m task6.run --skip-viz   # 只构图与检查
python -m task6.graph stats      # 查询图规模
```

构图流程：

1. 读取 5 个输入文件并计算 SHA-256；
2. 聚合 task2 POI、按 task3 别名归一；
3. 过滤低频候选与边界动作；
4. 建景区、文档、POI 节点；
5. 按 `route_id` 排序建路线和步骤，连接 `HAS_STEP`/`NEXT`/`VISITS`；
6. 归一活动、连接时段；
7. 建条件、条件类型、`RELATES_TO`；
8. 导出 `nodes.csv`、`edges.csv`、`graph.json`、`graph.graphml`、`stats.json`；
9. 运行质量检查并生成 `quality.json`、`QUALITY.md`；
10. 生成静态 PNG 与交互 HTML。

实现上刻意没有引入 Neo4j：本实验规模只有 583 个节点、1,751 条边，NetworkX 足够完成构图、查询和导出；`graph.graphml` 可以在需要时直接导入 Gephi 或 Neo4j。这样提交物不依赖数据库服务，组员和老师可以直接复现。

### 6.6.4 缺失与数据质量

图谱写完了，但数据缺口必须明确：

1. **时间覆盖低**：250 个步骤中只有 31 个有显式时段（上午/中午/下午），125 个有日期/天数，31 个有时刻；219 个步骤没有时段。task7 不能把“没有时段”默认为上午或下午，只能作为未知处理。
2. **时长覆盖低**：只有 12 个步骤有游玩时长、14 个步骤有交通时长，无法支撑精确到小时的行程排程。
3. **7 个步骤没有 POI**：4 个是边界动作（出沟/进景区），3 个在 task3 中就没有 POI（到达景区/出景区/摆渡车）。这些步骤仍保留活动与顺序，但不参与 POI 级路径。
4. **2 条路线没有起终点**：九寨沟的进景区/出沟路线首尾是边界动作，未虚构 `STARTS_AT`/`ENDS_AT`。
5. **条件链接不完整**：41 条条件中 20 条链接到具体 POI，21 条只到景区/文档级；字符串匹配可能漏掉“这里”“那边”等指代，也可能把泛称误链。边上的 `matched_text` 和 `match_field` 用于复核。
6. **task5 未完成真实人工确认**：41 条条件的 `review_status` 仍是“待真实人工确认”，图谱不把它当金标准。
7. **task2 的 TIME/TRANSPORT 未单独建节点**：它们参与了统计和活动归一，但没有形成“时间表达式”“交通方式”节点；如果 task7 需要按交通方式查询，需要下一版扩展。

## 6.7 局限与改进方向

本章的主要局限不在“图能不能画出来”，而在“图上的语义是否足够细”：

- **条件到 POI 的连接是表面匹配**。例如“时间有限 → 选珍宝馆”能正确链接，但“带娃 → 在神武门收尾”只链接到神武门，没有表达“带娃”与“神武门收尾”之间的因果。后续可以引入 LLM 关系抽取或规则模板，把条件—建议—POI 变成三元组，并做人工抽样评估。
- **时间粒度不足**。当前只能表达“上午/中午/下午”和少量时刻，无法表达“约 2 小时”“避开 10:00 人流”等。task7 若要做时间规划，需要把 task2 的 TIME 实体和 task3 的时长字段进一步结构化。
- **路线步骤的活动是粗粒度归一**。12 个活动节点能支撑“参观/乘车/步行/用餐”级别的查询，但不能区分“拍照”“排队”“换乘索道”等细粒度动作。
- **没有做图嵌入或相似路线计算**。本章的重点是融合与可视化；如果要做“相似路线推荐”，可以在 POI 序列上做编辑距离或图嵌入。
- **规模上不需要 Neo4j**。当前 583 节点、1,751 边，NetworkX 足够；如果后续扩展到全国景区，应该迁移到 Neo4j 或 NebulaGraph，并把本章的 `nodes.csv`/`edges.csv` 作为导入源。

## 6.8 本章小结

本章完成了三件事：

1. **融合**：把 task1 文档、task2 实体、task3 路线、task5 条件合成一张 583 节点、1,751 边的异构图谱；291 个 task3 实体引用全部精确对齐 task2，70 个 POI 同时被官方与游客文档提及。
2. **建图**：定义了 9 类节点、14 类边，保留 `doc_id`、字符区间、来源类型和条件审核状态；导出 CSV、JSON、GraphML，并提供 `task6/graph.py` 查询接口。
3. **验证与展示**：18 项自动检查全部通过；三个景区子图各自连通、无孤立节点；用故宫和九寨沟的静态图、三个景区的交互图展示了核心节点、典型路径和条件建议。

图谱的边界也很清楚：时间与时长覆盖不足、条件链接依赖字符串匹配、task5 尚未完成真实人工确认。这些缺口会在第 7 章 Agent 的设计中显式处理——Agent 只能查询图上已有的关系，缺失信息应回答“未知”或给出保守建议，而不是让语言模型补全。
