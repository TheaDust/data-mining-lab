## 页面与操作

首页：景区选择、自然语言需求框，附3条可执行示例；可展开填写游览时长、同行人、必去与避开景点、体力偏好。未填写的信息保持未知。

规划工作区：左侧对话及需求摘要，右侧行程卡片与路线顺序图。窄屏改为对话/行程切换。生成时显示实际阶段状态，例如检索路线、筛选建议、校验方案；不显示模型私有思维链。

行程卡片：步骤序号、景点、活动、原文已有时间、适用建议，以及来源入口。原文时间、规划估计和未知状态分别标记。首版优先保持路线原有顺序，不将不同路线步骤任意拼成无依据的路线。

来源抽屉：显示route_id、pair_id、doc_id、原文片段、URL及审核状态。普通使用界面以可读标题为主，技术ID与工具JSON放在可展开的运行记录中，便于实验验收。

继续调整：例如去掉某景点、修改游览天数或减少活动。保存上一版约束及结果；修改后重新检索和校验，以新版完整行程替换。不能承诺无距离数据支撑的“最短步行”。

## Agent核心

流程：解析需求 → 检查缺失与冲突 → 模型选择并调用图谱工具 → 判断证据适用性 → 选择候选路线 → 生成结构化行程 → 程序校验 → 返回结果或追问。

角色划分：模型负责自然语言理解、语义适配、工具选择、结果表述；Python负责工具白名单、参数校验、图谱读取、来源关联、硬约束检查、循环上限和日志。只在有明确证据时判定约束已满足，区分满足/冲突/未知。

工具接口建议：

- list_scenic_spots：调用GraphStore.scenic_spots。
- search_routes：调用routes，可按景区和来源筛选，返回候选route_id及概览。
- get_route_details：调用route_sequence，附路线源文档与证据。
- find_routes_through_poi：调用routes_through_poi，处理别名、歧义和无结果。
- search_condition_advices：调用conditions按景区取得候选，再由模型判断完整条件是否适用。类别相同不等于满足条件；否定、AND/OR及文档内局部路线指代必须保留。
- get_source_evidence：经doc_id、pair_id定位源文档及条件证据；需要时读取task5最终映射表，补齐图谱节点中未完整携带的sources。

工具统一返回status、data、evidence与limitations；状态含ok、no_match、invalid_input、error。对模型传入的未知参数或ID拒绝执行，不能让模型执行任意Python或数据库语句。

运行状态包含request_id、原始请求、已知约束、缺失字段、工具调用及返回、候选路线、条件适用性判断、最终方案、验证问题。限制工具调用轮数；校验失败最多修复一次，再失败返回有依据的部分结果及未解决问题。

验证至少检查：景区一致、引用ID真实且来自本次工具返回、必去/避开景点、原路线相对顺序、条件的否定含义、来源能回查、事实时间与估计时间区分。缺少行走距离、开放时间、预约和通行数据时，不能宣称完成严格时空最优规划或当前可执行性验证。

## 实施顺序和验收

1. 安装最小Python依赖，验证现有GraphStore及证据读取；冻结输入版本。
2. 实现工具Schema、结构化输出及DeepSeek适配，先跑通命令行的真实工具闭环。
3. 实现约束与证据验证，保存真实调用日志。
4. 实现React+TypeScript前端及FastAPI接口，前端不持有模型密钥；以阶段事件更新进度和最终行程。
5. 完成多轮修改与来源展开，覆盖窄屏、加载、空结果和错误状态。
6. 测试老人/亲子/情侣至少3类正常场景；补充缺少景区、未知景点、必去与避开同一景点、无适用建议、时间数据不足、模型调用失败等场景。离线测试可使用显式测试替身；实际Agent验收必须包含真实模型调用日志，不能混报。
7. 产出运行说明、依赖、环境变量名、测试记录、完整演示、实验7报告与实际失败案例。不得提交密钥；不虚构人工评估或运行结果。

首版成功标准：用户输入需求后，系统真实查询本组图谱，产出能回查依据的行程；用户修改需求可得到重新验证的结果。页面可用性和实验要求同时满足。
