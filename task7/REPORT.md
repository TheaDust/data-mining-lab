# 实验项目7 程序性知识应用与旅游规划Agent

负责人：房立志（成员C，学号202430550430）
实验日期：2026年11月8日

本实验将前序实验的知识图谱接入旅游规划Agent，形成可在本机浏览器使用的“山行”应用。用户输入景区、同行人和时间等要求后，系统调用图谱工具检索路线与条件建议，再输出具有原文依据的行程。当前实现支持北京故宫、杭州西湖和九寨沟。评价区分离线程序检查、真实模型场景检查与人工界面验收，不将小样本通过率解释为知识准确率。

## 7.1 架构与LLM接入

系统采用React和TypeScript前端、FastAPI后端、DeepSeek语言模型及NetworkX图谱查询接口。上游输入为实验6的`graph.json`，并通过`doc_id`关联实验1清洗文档，通过`pair_id`关联实验5最终条件映射表，保留其审核状态。图谱包含583个节点、1751条边，覆盖23条路线和250个步骤；条件建议共41条。

数据流为：用户请求 → JSON需求解析 → 缺失/冲突检查 → 模型选择工具 → Python实际执行图谱查询 → 模型读取返回结果 → 提交结构化方案 → 条件复核与程序校验 → 前端展示。代码入口为`task7/agent.py`的`Planner.run`。模型通过实际工具调用读取图谱结果。前端以NDJSON接收阶段状态，使用react-force-graph-2d呈现真实查询子图。

模型使用`deepseek-flash`，温度为0，关闭thinking模式，每次输出上限4500 tokens。通过`DEEPSEEK_API_KEY`读取本机凭据，可用`DEEPSEEK_MODEL`与`DEEPSEEK_BASE_URL`切换模型和接口。HTTP请求超时90秒、连接超时15秒；仅对429与部分5xx响应最多重试一次。超时可能已发生服务端推理，因此不自动重发超时请求。

需求解析使用JSON Output和Pydantic校验，输出景区、用户原始时长、天数、同行人、偏好、必去、避开及用户明确提供的天气。对话中继承上一轮约束，再根据新消息更新。未提及天气、体力或是否初入高原时，保持未知，不能通过常识补成用户事实。

核心Prompt要求：只使用本次工具返回的事实；先查询路线再读取详情；不添加新景点和步骤；保留原顺序；有必去与避开冲突时追问；时间未知就标记待定。Prompt原文位于`PARSE_PROMPT`和`AGENT_PROMPT`，可直接核查。

## 7.2 图谱查询工具封装

工具在`task7/tools.py`定义，参数Schema来自Pydantic，禁止额外字段，并仅开放白名单函数。每次请求独立维护已检索路线、已读取详情、建议及文档ID集合。

| 工具 | 输入 | 实际查询及输出 |
|---|---|---|
| search_routes | scenic_spot | GraphStore.routes及route_sequence；候选路线ID、来源、原始时长、步骤顺序摘要 |
| get_route_details | route_id | 仅允许本次候选；返回route_steps完整步骤、证据和来源文档 |
| search_condition_advices | scenic_spot | GraphStore.conditions；返回完整条件、建议、pair_id和审核状态 |
| get_source_evidence | doc_id | 仅允许本次来源；返回clean_text、标题、URL和来源类别 |
| submit_plan | status、message、route_id、orders、advice、rationale | 提交最终方案，触发校验；不是任意代码执行入口 |

统一查询结果包含`status`和`data`或`error`。状态区分ok、no_match、invalid_input；未知函数、跨景区参数、未检索ID和额外字段会被拒绝。未检索到数据不伪装成正常命中。

例如真实亲子场景按顺序调用search_routes、search_condition_advices、get_route_details和submit_plan。完整参数与实际返回保存在`task7/results/demo.json`，可看到模型选择的路线及返回的步骤，证明工具实际参与了最终结果。

## 7.3 闭环编排与回退策略

后端实现显式Python状态机和DeepSeek原生tool_calls循环：将模型返回的工具请求加入消息历史，执行对应函数，以`role=tool`和对应`tool_call_id`回传结构化结果，再请求下一步决策。最多8轮、20次工具调用；最终方案校验失败可修复一次，第二次仍失败就返回明确错误，不展示未经校验的行程。

最终方案只选择一条已读取的路线，以及该路线的原步骤序号。程序检查步骤非空、唯一、递增、属于路线；检查必去、避开景点及原文天数是否超过预算。地点匹配只使用精确名称或图谱已记录别名，不模糊合并父子景点。行程中的POI、活动、时间和证据均由真实步骤记录构建，不采用模型自行填写的步骤正文。

条件建议另做一次独立模型请求，逐条判断matched、unknown或contradicted。只有matched进入最终卡片；缺少判断或条件未明确时丢弃。条件建议文本从上游完整取回，避免在润色时丢掉否定或限定。该复核仍属于LLM辅助过程，并非人工金标准。

回退包括：缺少景区或时长时追问；黄山等未覆盖景区返回no_match；必去和避开同一景点时先澄清；不存在的必去景点返回无匹配；模型认证、余额、限流、网络或格式异常时返回可读错误。界面保留对话以供继续修改。更新请求处理期间，右侧切换到本次检索网络，完成后展示新行程；未通过检查时返回追问、无匹配或明确错误。

## 7.5 一次完整执行与失败分析

示范输入：“带孩子去故宫玩半天，必须去太和殿，不去珍宝馆”。解析结果为北京故宫、半天、days=1、同行孩子、must_visit=[太和殿]、avoid=[珍宝馆]。Agent检索故宫路线及条件建议，读取游客“半天精华线”的原始6步，选择原步骤1、2、3、4、6，删除包含珍宝馆的第5步。

最终路线为午门 → 太和殿/中和殿/保和殿 → 乾清门/乾清宫/交泰殿/坤宁宫 → 御花园 → 神武门。景点及相对顺序均来自实际读取的路线；系统没有跨路线拼接。原文未标明各步准确时间，界面显示时间待定；“2.5～3小时”只作为原路线资料，不保证删减后的行程已得到严格时间验证。输入、约束、工具参数、返回、条件复核及结果均见`results/demo.json`。

失败现象一：首次真实老人九寨沟请求中，模型选择了R00006“初入高原的朋友→第一日尽量不进行剧烈运动”，但用户没有说初入高原。原记录保存在`results/failure_before_advice_audit.json`。原因是模型将目的地常识转成用户事实，单纯校验pair_id和用户引用字符串不能保证条件完整成立。改进为独立条件复核并对unknown采用保守拒绝；后续老人验收中R00006被判unknown并移除。这仍可能产生误拒，需要人工标注评估。

失败现象二：上游250个步骤只有31个有明确时段。故宫示范多数步骤没有时刻，无法按用户半天需求验证每段停留和移动时间。其原因属于数据覆盖与约束可计算性不足，不是单纯增加Prompt就能解决。当前不补造时间，显示待定并说明删减后交通衔接未核实。后续应区分原文时间、可核验运营信息和带区间的估计，才能计算时间可行性。

失败现象三：最新九寨沟演示中，独立复核将R00005、R00006、R00037均判为unknown，最终advice为空，但message仍出现“初到高原当天别做剧烈运动”和“下午注意防晒”等内容，还说“然后直接返回沟口”，而所选步骤末项是长海至五彩池，并未包含返程步骤。原因是结构化建议在复核后被删除，先前生成的自然语言摘要没有重新生成，且摘要未进行逐句事实和条件校验。此问题仍未修复，不能把“结构校验通过”等同于“整段回答已核验”。可行的下一步是校验后再生成摘要，要求每条建议绑定已通过审核的pair_id，每项路线叙述绑定实际step_id，并增加“删除建议不得在摘要中复现”和“未选返程不得宣称已安排返程”的回归测试。证据保存在results/demo_jiuzhaigou.json。

工程联调还发现首次启动后端早于前端构建时，静态目录尚不存在导致首页404。确认构建完成后重启服务恢复；`start.sh`在启动服务前检查前端构建，避免首次运行顺序错误。

### 图谱检索可视化与交互联调

本次使用react-force-graph-2d的官方directional-links-particles示例作为实现参考，复用力导向布局、定向粒子和拖动缩放API，不使用React Flow流程图。GET /api/graph返回任务6的真实节点ID、节点类别和真实边；graph_view.py按本次工具结果生成节点集合。前端先显示完整图谱，再按目的地、已读取路线、最终步骤与来源依次聚焦，保留节点坐标，渐隐无关节点并适配视野。粒子展示关系方向，不等于模型思维过程或最短路径算法；回查来源可能补入节点，因此不保证节点数严格递减。

## 7.7 旅游规划Agent示范用例

示例输入：“我想带父母去九寨沟玩一天，希望节奏轻松一些。请帮我安排游览路线，并说明推荐理由和需要注意的事项。”该例用于界面展示和实际运行记录，不作为新的独立准确率测试。

本次解析得到景区九寨沟、duration为一天、days为1、travelers为父母、preferences为节奏轻松；必去、避开列表为空，天气保持null。实际调用依次为search_routes、search_condition_advices、get_route_details、submit_plan，四次工具返回均为ok。完整记录的request_id为e5b535252a4843218a710b9e62ce6abe，保存为results/demo_jiuzhaigou.json。

网络从全图583个节点聚焦到九寨沟192个节点，再到已读取路线的45个节点，最终保留33个节点。最终结构化方案为官网“一日精华游”的11个原步骤，所选路线ID、原始order、step_id和来源均保留；不把界面节点数当作推荐质量指标。三条条件建议被独立复核为unknown后移除，最终建议卡片数为0。自然语言摘要仍有未同步过滤的内容，按7.5记录为失败案例。

演示视频为videos/山行_九寨沟长辈游_演示.mp4，分辨率1440×900，H.264格式，约54秒。视频记录示例文本输入、实际发送请求、图谱检索收敛、结果出现、收起网络及打开原文依据。保留真实工具和模型响应，没有用预置答案替代本次请求。演示步骤为：输入上述需求并发送；观察全图到子图；检查11步行程；打开第一步“查看依据”；核对来源，再回到行程。视频不能替代结构化日志和代码检查。

## 总结反思素材

现有方案至少有四条局限：知识缺乏完整时空信息；条件适用性依赖模型且缺少人工金标准；只在现有单条路线内保守选取，无法规划未出现的跨路线连接；模型生成的概括性文字未得到逐句形式化验证。因此“通过来源检查”不应解释成“所有回答正确”或“行程现实可行”。

若有一个学期，优先突破“带不确定性的时间与体力约束规划”。先人工标注一批真实路线的时长区间、换乘方式与步行强度，区分原文和估计；在已有路线图上建立区间时间预算模型；对比纯LLM、当前检索加校验、区间约束规划三种方法。在相同输入与固定数据划分下，衡量必去覆盖率、冲突率、时间超限率、来源一致性与人工可执行性评分。可能的新问题包括估计误差、不同人群速度差异及未知通行条件，应保留未知状态并报告置信区间，而不是将缺失值简单填成平均值。
